# PROTOTYPE/DRAFT Bike Downtown Ottawa. CSAP Commuter Map

A simple standalone map highlighting **car-separated bike routes from Ottawa's
suburbs to downtown**, built for the **Cycling Safety Awareness Program (CSAP)**
administered by [Envirocentre](https://www.envirocentre.ca) on behalf of the
City of Ottawa.

The goal: show people who commute downtown by car that there is a safe,
mostly car-free bike route from their neighbourhood and roughly how long
it takes.

## What's on the map

**Ten commuter corridors**, each ending at Laurier Avenue West & O'Connor
Street downtown, routed along the NCC multi-use pathway network wherever
possible:

| Route                         | Distance | Time    | Car-free |
| ----------------------------- | -------- | ------- | -------- |
| Barrhaven                     | 21.8 km  | 78 min  | 63%      |
| Blackburn Hamlet / Gloucester | 17.7 km  | 66 min  | 58%      |
| Findlay Creek / South Keys    | 19.7 km  | 72 min  | 72%      |
| Greenboro                     | 11.9 km  | 45 min  | 68%      |
| Kanata North                  | 27.8 km  | 94 min  | 88%      |
| Nepean                        | 18.9 km  | 65 min  | 92%      |
| Orléans                      | 23.2 km  | 82 min  | 81%      |
| Orléans South                | 30.4 km  | 107 min | 71%      |
| Pineview                      | 10 km    | 36 min  | 65%      |
| Stittsville / Kanata South    | 31.2 km  | 116 min | 97%      |

These figures change whenever a corridor is edited, and `npm run routes` prints the
current set — treat the table as a snapshot rather than the source of truth.

A separate South Keys / Hunt Club corridor was retired: Findlay Creek / South Keys
passes within 80 m of the Juno Beach bridge on the Sawmill Creek Pathway, so it
already served the same riders over almost the same alignment.

Figures are for the ride **to** downtown. Two corridors differ slightly on the
way back: Blackburn Hamlet / Gloucester (17.1 km / 64 min) and Findlay Creek /
South Keys (21.3 km / 76 min) — see below. Times come from the model described under
"Ride time estimates", not from distance alone.

Other features:

- **Line thickness shows how protected each section is** — thick where the
  route is car-free, thin where it shares the road with traffic. Each route
  also reports the share of its length that is car-free.
- **Ride times account for stopping**, not just distance, so a pathway corridor
  reads faster than an on-street one of the same length (15–17 km/h effective).
  The section popup breaks out how much of the estimate is spent at red lights.
  See "Ride time estimates" below.
- **Some sections are one-way.** Where the better ride differs by direction,
  the route splits into two lines with **arrows showing which way to ride**.
  Blackburn Hamlet / Gloucester does this either side of St-Laurent Boulevard:
  outbound it swings north via Guy Avenue, homeward it stays on McArthur Avenue.
  Findlay Creek / South Keys splits at the Rideau River footbridge and the two legs stay
  apart the rest of the way in: outbound it climbs University Drive, crosses
  Bronson Avenue and continues through the Glebe on residential streets, while
  homeward it follows the pathways east of the campus through Brewer Park and
  then the canal. The outbound leg is pinned to both ends of the protected
  stretch of Glebe Avenue, because unaided the router prefers Clemow Avenue a
  block north, which has no cycling infrastructure at all. Arrows appear from zoom 12 in, and the side panel explains
  them when such a route is selected.
- Selecting a route (from the list or by clicking its line) isolates it and
  zooms to it; clicking the selected route again describes that section —
  including which direction it is for, on a one-way section.
- English/French toggle and a high-contrast accessible style variant.

## How it's built

Everything is static — no server and no build step to deploy. Host the folder
anywhere; GitHub Pages works out of the box via the included workflow.

| File                                                 | What it is                                                                                                                |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `index.html`                                       | The whole app: MapLibre GL map, route list, legend, i18n                                                                  |
| `style-default.json`, `style-high-contrast.json` | MapLibre styles, generated (see below)                                                                                    |
| `routes.geojson`                                   | The ten routes, generated by`tools/fetch-routes.mjs`                                                                 |
| `time-pills.json`                                  | "35 min left" markers along each route, written by the same script                                                       |
| `assets/`, `fonts/`                              | City of Ottawa logo and favicon; Mulish, the City's brand typeface, self-hosted so the page makes no third-party requests |
| `vendor/`                                          | MapLibre GL JS 5.19.0, vendored                                                                                           |

### Regenerating the map style

The style is adapted from the open-source
[whereto.bike / bike-app-astro](https://github.com/eljojo/bike-app-astro)
cycling map ("Oasis in the Desert" design). To regenerate, check out that
repo as a sibling folder named `bike-app-astro-main`, then run **both** steps
in order:

```sh
npx tsx tools/generate-style.mts <THUNDERFOREST_API_KEY>
node tools/street-contrast.mjs
```

`street-contrast.mjs` is a post-processing pass that makes the local street
grid legible (the upstream style keeps streets as a near-invisible backdrop).
**Running the generator alone silently discards it** — always run the second
step afterwards.

Tiles are [Thunderforest outdoors-v2](https://www.thunderforest.com/docs/thunderforest.outdoors-v2/)
vector tiles (OpenStreetMap data). The API key baked into the style JSON is a
usage-limited free-tier key; regenerate with your own if needed.

### Regenerating the routes

Routes are computed by the public [BRouter](https://brouter.de) instance using
the `trekking` profile, with via-points pinning each corridor to the intended
pathway. Edit the corridor definitions in `tools/fetch-routes.mjs` and run:

```sh
node tools/fetch-routes.mjs
```

Two things worth knowing when editing corridors:

- Points are `[longitude, latitude]` — the reverse of how Google Maps displays
  them. A swapped pair produces a `datafile ... not found` error from BRouter.
- Where routes overlap, the one appearing **later** in the `CORRIDORS` array is
  drawn on top.
- `MANUAL_TRIMS` removes individual points from the drawn line to tidy up
  crossing artifacts. It is cosmetic only and does not change the routing —
  read the comments there before adding a box, as it is easy to delete a real
  turn by accident.
- A stretch that looks like it should be car-free but draws thin is usually a
  routing problem, not a tagging one. See "When a protected section draws thin".

#### When a protected section draws thin

Safety classes come straight from the OSM tags, which is what keeps the car-free
percentages honest. So when a section you know is protected draws thin, work
through it in this order — the first cause is by far the most common, and the one
that bit Glebe Avenue:

1. **The route isn't on it.** Protected tracks are often mapped as their own
   `highway=cycleway` way running a few metres off the roadway, and BRouter may
   put the line on the road, or on a different street entirely. Check what the
   route actually uses before assuming the tags are wrong:

   ```sh
   curl -s "https://brouter.de/brouter?lonlats=LON,LAT|LON,LAT&profile=trekking&format=geojson"
   ```

   The `WayTags` column of `messages` gives the tags for every stretch. Cross-
   reference with Overpass to find the parallel way and its node coordinates:

   ```
   [out:json];way[highway=cycleway](minlat,minlon,maxlat,maxlon);out tags geom;
   ```

   Then add **one** via on an interior node of that way. One is usually enough,
   and is better than more: a `oneway` track pinned at both ends can send the
   router doubling back to enter it from the far end.

2. **The tags really are stale.** Only after ruling out (1). Prefer fixing OSM
   upstream — it fixes this map, every other map, and needs no code. There is no
   override mechanism here on purpose; an earlier version had one and it papered
   over a routing bug rather than fixing it.

Glebe Avenue between Bank Street and O'Connor Street is the worked example. The
roadway carries `cycleway:right=lane`, which classifies as a painted lane, while
the real protected track beside it is a separate `highway=cycleway` way. The
corridor pins one via to that way, and the section then classifies as car-free
with no special handling.

#### Ride time estimates

Times are **not** BRouter's `total-time`. That figure is a constant-power physics
estimate (100 W pushing 90 kg, set in `trekking.brf`) for a rider who never
stops: it puts every corridor at 19–21 km/h and actually rates signal-dense
painted lanes *faster* than pathways, because they are straighter. Measured over
these routes it gave 20.0 km/h on car-free sections against 21.0 km/h on painted
lanes — backwards for our purpose.

What actually separates a pathway commute from an on-street one is stopping.
Across these corridors, painted lanes carry about **5.6 traffic signals per km
against 0.8 on cycleways**. So `fetch-routes.mjs` builds the time itself, in two
parts, from tags already present in the BRouter response:

- **cruise time** — segment length ÷ a free-flow speed from `CRUISE_KMH`, chosen
  by highway/cycleway tags, cut by `UNPAVED_FACTOR` where `surface` is gravel or
  similar. These speeds sit deliberately close together (17.5–18.5 km/h for
  anything ridable); the spread between routes is meant to come from stops, not
  from guessing that one surface is quicker.
- **stop delay** — an expected cost per traffic control the route passes, read
  from the `NodeTags` column: `SIGNAL_DELAY` for traffic signals, `STOP_DELAY`
  for stop and give-way signs, plus smaller costs for uncontrolled crossings and
  barriers.

This yields 15–17 km/h effective, and the ranking tracks infrastructure quality
(correlation between car-free share and effective speed is r ≈ 0.74) where the
old flat 18 km/h made every route's time a restatement of its distance.

Each route also publishes `stop_minutes`, which the section popup uses to say
*"includes about 4 min stopped at traffic lights"*, and `signals`, which is kept
for diagnostics only. **Do not put the junction count in user-facing copy.** It is
an over-count by construction (see the residual bias below), so a reader who knows
the corridor can check it and find it wrong — Orléans came out at 22 where a local
would say 10, because 21 of those are in the final 3 km through downtown. The
count barely moves the estimate (four signals is 40 seconds on an 80-minute ride),
so there is nothing to gain by printing it.

**Controls are de-duplicated per junction, and this matters more than it sounds.**
OSM maps one signalised intersection as several nodes — the junction node, plus a
signalised crossing node on each approach leg — and BRouter reports every one.
Charging each would bill a single intersection two to four times: on the `vanier`
corridor it
turned 21 real junctions into 49, adding six minutes of phantom waiting.
`summarizeControls()` collapses controls within `JUNCTION_RADIUS_M` (40 m) into
one event, charged for whichever control in the cluster costs most. Note that the
clustering runs across a whole direction rather than per segment, because a
junction can sit exactly on a segment boundary — the `vanier` corridor's REJOIN does.

Route **ids do not track the display names**, because several corridors were renamed
after their ids were set:

| id                 | label now                       |
| ------------------ | ------------------------------- |
| `blackburn-hamlet` | Pineview                        |
| `vanier`           | Blackburn Hamlet / Gloucester   |
| `alta-vista`       | Greenboro                       |
| `findlay-creek`    | Findlay Creek / South Keys      |

Note that `blackburn-hamlet` is *not* the Blackburn Hamlet route. References to a
corridor in the notes below use the id, in backticks, to stay unambiguous.

The radius wants care. 40 m is chosen because downtown's multi-lane crossings are
wider than the suburban ones it was first tuned on: at 30 m the Orléans route still
billed single intersections twice, as a `crossing=no` junction node plus a
`crossing=traffic_signals` node 40 m further along. Do not push much past 40 m —
downtown blocks are roughly 100 m, so by ~80 m the clustering starts swallowing
genuinely separate intersections.

**Recalibrating.** `SIGNAL_DELAY` and `STOP_DELAY` are the only tuned numbers, and
their weight varies — around 4% of total time on Stittsville against low double
figures on the stop-heavy urban routes. To fit them, time two real rides (one short
stop-heavy corridor such as Alta Vista, one long pathway one such as Kanata North)
and solve for the pair; two measurements fit two constants. Everything else in the
model is either measured (distances, junction counts) or a narrow band that barely
moves the result.

For reference, when the `vanier` corridor still ran 8.4 km from Vanier itself,
Google Maps gave 28 min against this model's 33 — Google's figure implies 18 km/h,
which leaves no room for stopping at 21 signalised junctions, so some of that gap
was theirs rather than ours. Worth repeating the comparison against a real ride on
whichever corridor you calibrate.

One residual bias: `NodeTags` flags every junction the route *passes*, including
ones a rider rolls straight through with priority. De-duplication fixes the
multiple-nodes-per-junction problem but not this one, so counts still lean high.
Fit the delay constants downward to absorb it rather than trying to work out which
junctions genuinely require a stop.

Elevation is deliberately ignored. BRouter does return it (the script strips a
third coordinate from each point), but Ottawa is flat enough that it would not
earn the complexity — these routes show 21–67 m of filtered ascent over 8–30 km.

#### Time-remaining pills

Each route carries markers counting down the time left to downtown — `1 hr 15 min`,
`45 min`, and so on. Distance markers would be the conventional choice, but time is
the number someone new to bike commuting can act on.

They also answer a presentation problem. The headline figure is the whole corridor
end to end, and hardly anyone rides all of it, so a 30 km route can read as
hopeless when a rider joining partway would only face half of it. Pills let people
find their own starting point on the line.

- Positions come from `timePills()`, which walks **the same cruise + de-duplicated
  delay model as the headline estimate**, so a pill and the route's stated time
  cannot drift apart.
- Steps are set by `PILL_STEP_MINUTES`: 15 minutes normally, 10 for routes of 50
  minutes or less so short corridors still get about four markers. A step **must** be
  a whole multiple of 5 — `timePills()` aborts the build otherwise, because a pill
  reading "1 hr 22 min" would claim a precision the estimate does not have.
- Output goes to **`time-pills.json`**, not `routes.geojson`, because
  `boundsForId()`, `allBounds()` and `renderRouteList()` all assume every feature
  in that file is a LineString. It follows the same pattern as `photos.json`.
- Only the selected route shows its pills; ten routes' worth at once is
  unreadable. They are `pointer-events: none` so they never swallow a click meant
  for the route line, and their labels re-render on a language switch.
- Pills follow the **outbound** direction. On a route with a homeward branch the
  branch carries none, since "time to downtown" is not what a rider on it is
  asking.

#### Routes that differ by direction

A corridor normally has one `points` array. To make part of it one-way, give it
`segments` instead — each is routed as its own BRouter request:

```js
segments: [
  { points: [START, SPLIT] },                    // ridden both ways
  { dir: 'towork', points: [SPLIT, ...,  REJOIN] }, // outbound only
  { dir: 'home',   points: [SPLIT, REJOIN] },       // return only
  { points: [REJOIN, ..., DOWNTOWN] },           // ridden both ways
]
```

Things to get right:

- **Consecutive segments must share an endpoint**, or the drawn lines will not
  meet. Pick split and rejoin coordinates that already lie on the route rather
  than inventing them; the script reports nothing if they drift, but the map
  will show a visible gap.
- Write a `home` segment **suburb-first like every other segment**. The script
  reverses its geometry on output, and that reversal is what makes the homeward
  arrows point homeward — the map draws arrows along coordinate order.
- **Rejoin where the branches actually converge**, not merely somewhere further
  along. Any stretch both branches cover gets emitted twice, once per direction,
  and the map then draws opposing arrows along a path that is really two-way. An
  interim version of Findlay Creek rejoined at the downtown end of the canal and
  double-drew 4.8 km of a 6.2 km branch that way. A corridor whose two legs
  genuinely differ the whole distance needs no rejoin at all — Findlay Creek now
  runs both legs from the split straight to `DOWNTOWN`.
- Only directional segments get a `dir` property in the output, and the map's
  arrow layer keys off `dir`. Shared sections stay unmarked.
- **Arrows hide where another route is drawn on top.** At full strength every
  corridor is equally visible, so arrows on a one-way section running underneath
  another route read as describing *that* route — Findlay Creek / South Keys
  under Greenboro along O'Connor Street being the case that prompted this. The
  build splits each directional feature into runs by whether another corridor
  shadows it (within `SHADOW_TOLERANCE_M`, 15 m) and marks the unshadowed ones
  `solo`. `arrowFilter()` in `index.html` then shows:

  | view | filter |
  | ---- | ------ |
  | no selection | `['all', ['has', 'dir'], ['has', 'solo']]` |
  | route selected | `['has', 'dir']` |

  Selecting a route dims the others to 0.12, so the ambiguity is gone and the
  full set of arrows is more useful than a partial one. Runs shorter than
  `MIN_RUN_M` (70 m, about one arrow spacing) are absorbed into their longer
  neighbour, otherwise arrows would flicker in and out while panning. Each run
  shares its boundary vertex with the next so the drawn line does not gap.

  Every run prints its share at the end of a run, and a corridor whose one-way
  section is *entirely* shadowed is called out — it would show no arrows at all
  until selected, which is worth knowing rather than discovering on the map.
- `distance_km` and `minutes` are the outbound figures. When the return differs,
  features also carry `distance_km_home` and `minutes_home`, which the section
  popup shows. The two directions are timed separately, so a route can take
  longer home even over a shorter distance if it crosses more signals.

### Favicon

`assets/favicon.svg` is the City of Ottawa logo mark, cut out of
`assets/ottawa-logo-white.svg` — the swoosh paths plus the circle subpath, with
the "ttawa" glyphs dropped and the white fill replaced by the logo's green
(`#00A78E`) and blue (`#1D4F91`). The circle shares a `<path>` element with two
of the letters in the source file, so it has to be split off at the subpath
level rather than by deleting elements.

`favicon-32.png`, `favicon-192.png` and `apple-touch-icon.png` are rendered from
that SVG as fallbacks. The touch icon is padded on a white background because
iOS composites home-screen tiles on a solid colour and ignores transparency.

### Photo bubbles (currently off)

An optional feature places round photo markers along a selected route showing
what the infrastructure looks like there. It is complete and tested but
disabled at the client's request: set `SHOW_PHOTOS = true` in `index.html` to
re-enable. Photos live in `photos/` and are listed in `photos.json`.
